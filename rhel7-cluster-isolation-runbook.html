RUNBOOK / CLUSTER-ISOLATION — 04

RHEL7 複製機での隔離クラスタ構築手順書
(現行環境に干渉しない「空クラスタ」の起動)

組織の標準手順(クラスタが組まれた状態からのアンインストール)に合わせるため、複製機 1 対でクラスタを起動する。ただし conf・CIB・認証鍵がすべて現行本番環境のコピーであるため、そのまま起動すると本番へ干渉する。本書は「設定は書き換え、鍵は作り直し、CIB は空にして起動する」方針で、現行に一切触れない隔離クラスタを組む。実障害 1 件(corosync activating ハング)の対処を組み込み済み。

対象マシン Azure 上の RHEL7 複製機 1 対(2 ノード)。現行本番機のクローン。現行機と同一セグメントに存在する。root で作業。
本書のゴール 複製機 2 台だけがメンバーの、リソースを 1 つも持たない「空クラスタ」が Online になること(C8 の実測確認まで)。アンインストールの前段として組むだけなので、VIP 等のリソース定義は持ち込まない。
干渉の 3 経路
(なぜ危険か)		 設定が現行の完全コピーであるため、無対策で起動すると:
① 通信層の混線 — nodelist が現行ノードを指したままだと、複製機が現行クラスタへ参加要求を投げる(authkey も同一なので認証でも弾かれない)。
② リソース起動の実害(最重要) — CIB も現行のコピーのため、クラスタ成立の瞬間に現行と同じ VIP を上げようとし、同一セグメントでの IP 重複=本番通信障害に直結する。
③ フェンシング誤爆 — CIB に現行機を指す STONITH 設定が残っていると、条件次第で現行サーバを強制停止しに行く。
対策の柱 設定は書き換え(C3・C4)、鍵は作り直し(C5)、CIB は空にして起動(C6)。さらに外向き FW ブロック(C2)を「書き換えをミスしても現行に届かない」最後の安全網として先に張る。②③は CIB を空にすることで根絶される。
前後の手順書 前提: RUNBOOK 03 の U0(実態確認)・U1(バックアップ /root/ha-backup/)完了済み。
本書完了後: 「次工程への接続」の節を経て、RUNBOOK 03 の U3(パッケージ削除)以降へ。
実施範囲の凡例 複製機・全ノード 複製 2 ノード両方で実施 / 複製機・代表ノードのみ どちらか 1 台でのみ実施

作業前の必読事項(全工程共通ルール)

  1. コマンドは手打ちせず、必ずコピー&ペーストで実行する。IP・クラスタ名など オレンジ表示 の箇所だけ実環境の値に置き換える。
  2. 各コマンドの直後に echo $? を実行し、0 なら成功・0 以外なら失敗。
  3. 各 STEP の確認が OK になるまで次へ進まない。特に C2(FW)と C6(CIB 空化)は、飛ばすと干渉経路が生きたまま起動することになる。
  4. corosync.conf・/etc/hosts の修正は複製 2 ノードで同一内容にすること。片系だけ直すと起動ハング(実障害①)の原因になる。
  5. 実障害①: corosync が activating のままハングする事象が実際に発生している。activating は「相方または現行を探し続けている」状態であり、放置してよい状態ではない。C7 の赤枠と付録 A-1 を必ず読むこと。
  6. クォーラム無効化の工程は本手順では不要(理由は付録 A-2)。組織の古い標準手順に「no-quorum-policy=ignore を設定」等があっても機械的に踏襲しないこと。

STEP C1

前提確認(実 IP と conf 現状の棚卸し)

複製機・全ノード 
ip -4 a | grep inet
grep -E 'ring0_addr|cluster_name|transport|mcastaddr|mcastport|secauth|crypto' /etc/corosync/corosync.conf
確認
  • 複製機 2 台の実 IP を控える。現行機の IP と重複していないこと(重複しているなら FW 以前の問題なので作業を止めて解消する)。
  • conf の現状値を控える: ring0_addr(現行ノードを指しているはず)、cluster_name、transport が udpu(ユニキャスト)か udp(マルチキャスト)か、secauth の on/off。C3 の書き換え内容がこれで決まる。
  • RUNBOOK 03 U1 のバックアップ(/root/ha-backup/)が取得済みであること。
STEP C2

外向き FW ブロックの適用(最後の安全網)

複製機・全ノード

説明: C3 以降の書き換えをミスしても現行に届かないよう、クラスタ起動前に「自分から現行宛」の通信を FW で塞ぐ。多層防御の位置づけ: FW(届かない保証)+ conf 書き換え(向かわない保証)+ 空 CIB(実害の根絶)。

C2-1. ブロック対象 IP の洗い出し

U1 のバックアップが宛先リストの原本になる。洗い出すのは 3 種類: ①現行ノードの実 IP(ring0_addr)、②現行 VIP(CIB 内 IPaddr2 の ip=)、③td-agent の転送先(match の host)。

grep -E 'ring0_addr|mcastaddr|bindnetaddr' /root/ha-backup/corosync/corosync.conf
grep -A3 IPaddr2 /root/ha-backup/cib-dir/cib.xml | grep -i ip
grep -B2 -A5 '<match' /etc/td-agent/td-agent.conf 2>/dev/null | grep -E 'host|port'
確認
  • ①②③の IP をリスト化したこと。mcastaddr(239.x.x.x 等)が出た場合はそれもブロック対象に加える。
  • td-agent を削除済みの場合は、バックアップ側 /root/td-agent-backup/td-agent/td-agent.conf から読む。

C2-2. 管理経路の確認(締め出し防止)

外向き DROP は宛先との通信全部(戻り含む)を殺すため、自分の SSH 経路を潰さないか先に確認する。

echo $SSH_CLIENT
確認
  • 表示された接続元 IP がブロック予定リストに含まれていないこと。現行機を踏み台に接続している場合はセッションが切れるので、先に別経路(Azure シリアルコンソール等)を確保する。

C2-3. ブロックの適用

firewall-cmd --state

running の場合(direct ルールで OUTPUT に DROP。対象 IP の数だけ繰り返す):

firewall-cmd --permanent --direct --add-rule ipv4 filter OUTPUT 0 -d 192.168.10.11/32 -j DROP
firewall-cmd --permanent --direct --add-rule ipv4 filter OUTPUT 0 -d 192.168.10.12/32 -j DROP
firewall-cmd --reload
firewall-cmd --direct --get-all-rules

not running の場合(iptables 直接。再起動で消える点に注意):

iptables -I OUTPUT 1 -d 192.168.10.11/32 -j DROP
iptables -I OUTPUT 1 -d 192.168.10.12/32 -j DROP
iptables -L OUTPUT -n --line-numbers | head
確認
  • 入れた分のルールが全部表示されること。firewalld 方式は permanent + reload により再起動後も維持される。
  • iptables 方式は揮発するため、再起動が発生したら再適用をルール化する(一次防衛は RUNBOOK 03 U2 の disable)。

C2-4. 効いていることの実測

ping -c 3 -W 2 現行ノードのIP
ping -c 3 相方の複製ノードのIP
確認
  • 現行宛が 100% packet loss、相方の複製ノード宛は通ること(絞りすぎていないことの確認)。

撤去タイミング(先出し): この FW ルールはアンインストール完了後の RUNBOOK 03 STEP Z で撤去する(--add-rule を --remove-rule に変えて reload)。firewalld の direct ルールは /etc/firewalld/direct.xml に残り続けるため、放置して RHEL8 化に持ち込むと「特定 IP と通信できない」将来障害の種になる。

STEP C3

corosync.conf の書き換え(4 点)

複製機・全ノード(同一内容) 
cp -a /etc/corosync/corosync.conf /root/corosync.conf.$(date +%F).bak
vi /etc/corosync/corosync.conf

書き換えるのは次の 4 点:

① nodelist の ring0_addr現行ノードのアドレス → 複製機 2 台の実 IP に変更。ホスト名運用なら C4 で hosts 側を直す方法も可だが、干渉防止の観点では IP 直書きが事故りにくい
② cluster_name現行と別名に変更(例: mycluster → mycluster-clone)。同名クラスタが同一セグメントに 2 つある状態を避け、crm_mon での見分けもつく
③ マルチキャスト設定
(transport が udp の場合のみ)		mcastaddr または mcastport を現行と別の値に変更。マルチキャストは「同じグループ宛に投げる」方式のため、nodelist を直しても同じ mcastaddr/port のままだと現行とパケットが混ざる。udpu(ユニキャスト)ならこの項目は不要
④ quorum セクションtwo_node: 1 があることを確認(変更ではなく確認。2 ノード構成の標準設定で、現行のコピーなら入っているはず。無ければ追記)
grep -E 'ring0_addr|cluster_name|two_node' /etc/corosync/corosync.conf
確認
  • ring0_addr に複製機の実 IP だけが出ること(現行 IP が 1 つでも残っていたら NG)。
  • cluster_name が新名称、two_node: 1 が存在すること。
  • 2 ノードとも同一内容にしたこと(片系だけの修正は実障害①の原因になる)。
STEP C4

/etc/hosts の整合

複製機・全ノード

説明: ring0_addr や CIB 内のノード名がホスト名運用の場合、その名前が複製機の IP に解決されるようにする。

getent hosts ノード名1 ノード名2
確認
  • 返る IP が複製機の実 IP であること。現行 IP が返るなら /etc/hosts を修正する(2 ノードとも同一内容)。
STEP C5

認証鍵の作り直しと配布

複製機・代表ノードで生成 → 相方へ配布

説明: 現行と同じ authkey を持ったままにしない(同一鍵は干渉経路①で「認証でも弾かれない」原因)。secauth: off の環境なら実効性は薄いが、作り直しておいて損はない。代表ノードで:

corosync-keygen -l; echo $?
scp /etc/corosync/authkey 相方複製ノードのIP:/etc/corosync/authkey
chmod 400 /etc/corosync/authkey
確認
  • 両ノードで md5sum /etc/corosync/authkey の値が一致すること(=新鍵が両方に配れた)。
  • 相方ノードでも chmod 400 /etc/corosync/authkey を実施したこと。
STEP C6

CIB を空にする(本手順の核心)

複製機・全ノード

説明: 干渉経路②(VIP 重複)と③(フェンシング誤爆)の根絶。現行リソース定義を持った CIB をディレクトリごと隔離退避する。Pacemaker は起動時に cib が無ければ空の設定で新規作成するため、これで「リソースゼロのクラスタ」が立ち上がる。

systemctl is-active pacemaker corosync
mv /var/lib/pacemaker/cib /root/cib-quarantine-$(date +%F); echo $?
ls /var/lib/pacemaker/
確認
  • mv の前に is-active が両方 inactive であること(activating を含め、動いたまま mv しない。activating の場合は付録 A-1 の手順で先に落とす)。
  • mv 後、/var/lib/pacemaker/ に cib が無いこと。
  • 退避先 /root/cib-quarantine-日付 は削除しない(U1 バックアップと並ぶ設定原本の一つ)。
STEP C7

起動(2 台とも)

複製機・全ノード
実障害 ①

症状: systemctl is-active corosync が activating のまま遷移しない事象が実際に発生した。activating は「起動処理の途中=corosync がピアを探し続けている」宙ぶらりんの状態。

原因は次の 2 パターン: (a) conf が現行のコピーのまま起動した — 現行ノードへ参加要求を投げ続けている危険な状態(C2 の FW が入っていれば実害は遮断されている)。(b) C3 修正後だが相方の複製ノードをまだ起動していない — two_node 構成の corosync は初回起動時に相方が見えるまで起動完了にならない(wait_for_all の動き)ため、片方だけでは activating で待ち続ける。

対策: (a) は即停止して C2〜C6 の完了状態を点検してからやり直す(停止手順は付録 A-1)。(b) は相方でも start すれば両方 active に遷移する。本 STEP は必ず「2 台とも起動」で 1 セットとし、片方だけの状態で判断しない。

下から順(corosync → pacemaker)に、2 台とも起動する:

systemctl start corosync; echo $?
systemctl is-active corosync
systemctl start pacemaker; echo $?
crm_mon -1
確認
  • is-active が active であること(activating のまま 1〜2 分変わらなければ実障害①。付録 A-1 へ)。
  • crm_mon -1 で 2 ノードとも Online、クラスタ名が C3 で付けた新名称であること。
  • Resources が 0(リソースが 1 つも無い)こと。何かリソースが見えたら即 systemctl stop pacemaker corosync で止めて C6 を見直す(古い CIB を読んでいる兆候)。
STEP C8

現行に干渉していないことの実測

複製機・全ノード

説明: 組めた「後」に、混線していないことを事実で確認する。3 つの干渉経路それぞれに対応する。

# 経路①: メンバーが複製機 2 台だけであること(現行 IP が見えたら即停止)
corosync-cmapctl | grep -E 'members.*ip'
# 経路②: 現行 VIP を自分が持っていないこと(何も出ないのが正)
ip a | grep 現行VIPのアドレス
# FW 網の生存確認: 現行宛が塞がれたままであること(100% loss が正)
ping -c 2 -W 2 現行VIPのアドレス
確認
  • members に出る IP が複製機 2 台の IP だけであること。
  • ip a に現行 VIP が出ないこと(空 CIB なので VIP を持っていないのが正)。
  • 現行 VIP 宛 ping が loss であること(C2 の FW が効いたまま)。
  • 3 点すべて OK なら、現行に一切触れない複製機 2 台だけの空クラスタが成立。本書のゴール達成。

接続

「クラスタが組まれた状態からのアンインストール」への引き継ぎ

複製機・全ノード

説明: これで組織標準手順の前提(クラスタが組まれた状態)が満たされた。アンインストールは以下の順で RUNBOOK 03 に合流する:

  1. 稼働状態の最終記録(代表ノード): crm_mon -1 > /root/uninstall-before-status.txt 2>&1 — Online 2 台・Resources 0 の状態を証跡化。
  2. 停止(全ノード・pacemaker → corosync の順): systemctl stop pacemaker; systemctl stop corosync; echo $?
  3. 自動起動解除(全ノード): systemctl disable pacemaker corosync; echo $?
  4. 以降は RUNBOOK 03 の U3(パッケージ削除)→ U4(残存物の掃除)→ U5(完了判定)→ STEP Z をそのまま実施。

読み替え 3 点: ① U4 で消す /etc/corosync には C3 で書き換えた conf と C5 の新鍵が入っているが、原本は U1 バックアップと C3 の .bak に保全済みなのでためらわず消してよい。② C6 の退避先 /root/cib-quarantine-日付 は /root 配下のため U4 では消えない — バックアップとして意図的に残す(STEP Z の閉域外複製の対象に含める)。③ C2 の FW ルールの撤去は STEP Z で行う(C2-4 末尾の先出し記載のとおり)。

付録A: 障害対処と補足

A-1

corosync が activating のまま遷移しない ★実障害①

複製機・全ノード

切り分け:

systemctl status corosync -l --no-pager
journalctl -u corosync --no-pager -n 50
grep -E 'ring0_addr|cluster_name' /etc/corosync/corosync.conf
  1. ring0_addr に現行 IP が残っている(C3 未実施/漏れ)→ パターン (a)。現行へ参加要求を投げ続けている状態なので即停止(下記)し、C2〜C6 を点検してからやり直す。
  2. conf は正しいが相方が未起動 → パターン (b)。相方ノードで systemctl start corosync を実行すれば両方 active に遷移する(two_node / wait_for_all の正常動作)。
  3. 上記以外(bind エラー、conf 構文エラー等)→ journalctl の出力を保存して個別対処。ring0_addr の IP が自ノードの NIC に実在するか(ip -4 a)を最初に疑う。

activating 状態の停止手順(stop が効かない場合のエスカレーション込み):

systemctl stop corosync; echo $?
systemctl is-active corosync

それでも activating / 残存する場合:

systemctl kill corosync
pkill -9 corosync
ps -ef | grep corosync | grep -v grep

ps が空になったことを確認してから、C2〜C6 の点検に戻る。

A-2

クォーラム無効化の工程が不要な理由

クォーラム(定足数)は「クラスタの過半数が揃っていないと動作しない」安全装置。2 ノード構成では「過半数=2 票中 2 票」となり片系障害で即動作不能になるため、corosync.conf に two_node: 1 を入れて「2 ノード特例(1 票でも動くが、初回は両方揃うまで待つ)」にするのが標準であり、C3-④ で存在確認している。したがって追加のクォーラム無効化操作は不要。

「クォーラム無効化」が必要になるのは、①1 ノードだけで一時的に動かす縮退運転(本手順は 2 台とも起動するので非該当)、② RHEL6 以前の旧世代手順の名残で no-quorum-policy=ignore を設定する流儀(現在は two_node が corosync 層で代替するため機械的踏襲は不要)の 2 場面のみ。また、アンインストールを 1 台ずつ時間差で進める場合でも、two_node: 1 があれば残った単独ノードは quorum を維持するので追加操作は不要。

A-3

C7 / C8 で NG が出た場合の対処早見

  1. crm_mon にリソースが見える → 古い CIB を読んでいる。即 systemctl stop pacemaker corosync(全ノード)→ C6 をやり直し(mv 漏れのノードがないか確認)→ C7 再実行。
  2. corosync-cmapctl の members に現行 IP が見える → 経路①が成立してしまっている。即停止(A-1 の停止手順)→ C3 の ring0_addr・③のマルチキャスト設定を再点検。C2 の FW が入っていたか(入っていれば実害は遮断されていた)も記録する。
  3. ip a に現行 VIP が出る → 空 CIB のはずなのに VIP を持った=1 と同根(古い CIB)。即停止して C6 へ。VIP 重複は本番影響のため、現行側の疎通(現行 VIP への到達性)を本番担当に確認依頼する。
  4. 2 ノードの片方だけ Online にならない → conf・hosts・authkey の「2 台同一」が崩れていないかを C3/C4/C5 の確認項目で再点検。

付録B: 用語の最小まとめ

空クラスタノードは Online だがリソース定義が 0 のクラスタ。本書のゴール。組織標準の「クラスタが組まれた状態からのアンインストール」の前提を、現行への干渉リスクなしで満たすための方式
activatingsystemd 上の「起動処理中」状態。corosync では「ピアを探して待っている」ことを意味し、active(完了)とも inactive(停止)とも異なる。実障害①参照
two_node / wait_for_all2 ノード構成向けの quorum 特例。1 票でも動作を許す代わり、初回起動時は両ノードが揃うまで待つ。C7 で「2 台とも起動」が必須な理由であり、クォーラム無効化が不要な理由(A-2)
udpu / udp(マルチキャスト)corosync の通信方式。udpu は nodelist の相手に個別送信、udp は mcastaddr のグループ宛に一斉送信。udp の場合は mcastaddr/port の変更(C3-③)をしないと nodelist を直しても現行と混線する
authkeycorosync のノード間認証鍵。複製機は現行と同一の鍵を持つため「現行クラスタに認証で弾かれない」— C5 で作り直す理由
CIB quarantine本書での CIB ディレクトリ退避(/root/cib-quarantine-日付)。削除ではなく隔離であり、RHEL8 再構築時の設定原本の一つとして STEP Z まで保全する
direct ルールfirewalld で iptables 相当のルールを直接記述する機能。外向き(OUTPUT)制限は firewalld の通常機能の範囲外のため、RHEL7 ではこれを使うのが定石(C2-3)
RHEL7 複製機での隔離クラスタ構築手順書 — 干渉 3 経路(通信混線 / VIP 重複 / フェンシング誤爆)対策と実障害 1 件(corosync activating)の対処組み込み済み
