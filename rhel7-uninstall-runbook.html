RUNBOOK / UNINSTALL — 03

RHEL7 複製機からの Pacemaker(crmsh 構成)/ td-agent アンインストール手順書

RHEL7 → RHEL8 バージョンアップ移行の前工程。現行機の複製マシン上から、サードパーティ製の Pacemaker 一式(Linux-HA Japan コミュニティ版)と td-agent を、設定・データ・ユーザーまで含めて過不足なく撤去する。複製機特有の事故ポイント 2 件(本番クラスタへの参加/ログの二重送信)への対策を組み込み済み。

対象マシン Azure 上の RHEL7 複製機 1 対(2 ノード)。現行本番機のクローンであり、本作業の後に RHEL8 へバージョンアップされる。root で作業。
削除対象ソフト ① Pacemaker 一式: pacemaker-1.1.21-1.el7 ほか(corosync / crmsh / pm_crmgen / pm_logconv-cs / cluster-glue 等)
② td-agent-3.5.1-0.el7.x86_64(fluentd のオムニバス版)
構成の判別根拠 Azure サポートの検出結果(crmsh / pm_crmgen / pm_logconv-cs あり・Red Hat 署名なし)と、リリース番号 1.1.21-1.el7 の形式から、Red Hat HA Add-On(pcs 系)ではなく Linux-HA Japan コミュニティ版の crmsh 主体構成と判断。したがって pcs コマンドは使わない(存在しない)。
本書の位置づけ 移行方式「複製 → 本書: ソフト撤去 → RHEL8 化 → ソフト再導入(RUNBOOK 01 / 02)」の第 2 工程。撤去の完了判定(付録 A-1 の 3 層判定)を満たすことが RHEL8 化工程への引き継ぎ条件。
実施範囲の凡例 複製機・全ノード 複製 2 ノード両方で実施 / 複製機・代表ノードのみ どちらか 1 台でのみ実施

作業前の必読事項(全工程共通ルール)

  1. コマンドは手打ちせず、必ずコピー&ペーストで実行する。特に本書は rm -rf を多用するため、タイプミスは即事故につながる。
  2. 各コマンドの直後に echo $? を実行し、0 なら成功・0 以外なら失敗。0 以外なら画面出力を保存してから対処する。
  3. 各 STEP の確認が OK になるまで次へ進まない。
  4. アンインストールは元に戻せない。したがって STEP U1 / F1 のバックアップは省略禁止。バックアップ一式は複製機の中だけでなく閉域外にも複製しておく(この複製機自体が後工程で RHEL8 化される=中身が変わるため)。
  5. 削除系コマンドの前後で「消す前の確認 → 削除 → 消えたことの確認」を対で実施する(本書の各 STEP はこの形で構成してある)。
  6. 複製機特有の事故ポイントが 2 件ある。①複製機が本番クラスタに参加してしまっている状態での作業(STEP U2)、②複製機の td-agent が本番の転送先へログを二重送信している状態(STEP F0)。該当箇所の赤枠を必ず読むこと。
  7. 証跡の残し方: 各完了判定コマンドの出力は >> /root/uninstall-after-check.txt 2>&1 を付けて追記保存する。RHEL8 化工程への引き継ぎ資料になる。

第 1 部: Pacemaker(crmsh 構成)の撤去

STEP U0

実態確認(パッケージ・repo の棚卸し)

複製機・全ノード

説明: 消す前に「何が入っているか」を確定させる。この出力が U3 の削除対象リストの根拠であり、U5 の完了判定の比較元になる。

rpm -qa | grep -Ei 'pacemaker|corosync|crmsh|pm_|cluster-glue|resource-agents|pssh|parallax|libqb|ldirectord' | sort > /root/uninstall-before-pkgs.txt; echo $?
cat /root/uninstall-before-pkgs.txt
rpm -qi pacemaker | grep -E 'Vendor|Packager|Signature'
ls /etc/yum.repos.d/
rpm -qa | grep -i repo
確認
  • パッケージ一覧が保存され、crmsh / pm_crmgen / pm_logconv-cs 等が実在すること(=crmsh 構成の裏取り)。
  • Vendor / Packager が Red Hat でないこと(Linux-HA Japan 等の表記のはず)。
  • /etc/yum.repos.d/ のサードパーティ repo ファイル名(例: pacemaker.repo)と、rpm -qa | grep -i repo に出るリポジトリ同梱パッケージ名(例: pacemaker-repo)を控えておく(U3・U4 で消す)。
  • 一覧に U3 の削除コマンドに無い名前があれば、U3 実行時にその名前を追加すること。
STEP U1

設定のバックアップ

複製機・代表ノードのみ + 各ノードの固有ファイル

説明: crmsh 構成のクラスタ設定は、RHEL8 側で pcs 構成に「翻訳」して再構築する際の唯一の原本になる。消す前に必ず取る。まず代表ノード 1 台で:

crm configure show > /root/crm-config-backup.crm; echo $?
cibadmin -Q > /root/cib-backup.xml; echo $?
crm_mon -1 > /root/uninstall-before-status.txt 2>&1

続いて各ノードで、手書き設定ファイル類を退避する:

mkdir -p /root/ha-etc-backup
cp -a /etc/corosync /root/ha-etc-backup/ 2>/dev/null; cp -a /etc/sysconfig/pacemaker /root/ha-etc-backup/ 2>/dev/null; ls /etc/ | grep -i -E 'pm_|logconv'
確認
  • crm-config-backup.crm の中にリソース定義(primitive 〜 の行)が入っていること。
  • 最後の ls で pm_logconv の設定ファイル(例: pm_logconv.conf)が見つかったら、それも /root/ha-etc-backup/ にコピーする。pm_crmgen で作った設計ファイル(Excel / .crm)が /root や /home にあれば同様に退避する。
  • バックアップ一式を閉域外にも複製したこと(共通ルール 4)。

クラスタが既に停止していて crm configure show が失敗する場合は、cp -a /var/lib/pacemaker/cib/cib.xml /root/cib-backup-raw.xml で設定 DB を直接コピーしておく。

STEP U2

クラスタの停止と自動起動解除

複製機・全ノード
事故ポイント ①

リスク: このマシンは本番機の複製であるため、ネットワーク的に本番クラスタに到達できる状態だと、複製機が本番クラスタの一員として参加してしまっている可能性がある。その状態で停止・削除作業を進めると、本番側でフェイルオーバー誘発などの実害が出得る。

対策: 停止前に必ず下の確認コマンドを実行し、Online に見えるのが自分自身だけであることを確かめる。本番側のノード名まで Online に見える場合は作業を中断し、ネットワーク隔離を先に行う。

crm_mon -1 | grep -i online
確認
  • Online 行に表示されるのがこのマシン自身(と、同時に撤去するもう 1 台の複製ノード)だけであること。本番ノード名が見えたら中断(事故ポイント①)。

説明: 停止順序は pacemaker → corosync。クラスタ管理下のアプリ(VIP・DB 等)もここで止まる。複製機とはいえ、止めてよい状態であることを確認してから実行する。

systemctl stop pacemaker; echo $?
systemctl stop corosync; echo $?

pm_logconv 等の付随サービスの有無を確認し、あれば停止する。そのうえで自動起動を解除する:

systemctl list-unit-files | grep -Ei 'pacemaker|corosync|logconv|ifcheck|hulft|diskd'
systemctl stop pm_logconv 2>/dev/null; systemctl disable pacemaker corosync; echo $?
確認
  • ps -ef | grep -E 'pacemaker|corosync|logconv' | grep -v grep の出力が空になること。
  • list-unit-files で見つかった付随サービスがあれば、それぞれ stop / disable したこと(名前は環境の実名に読み替え)。
STEP U3

パッケージの削除

複製機・全ノード

説明: Linux-HA Japan 構成の典型的なパッケージ群を一括削除する。U0 の一覧にあって下記コマンドに無い名前は、コマンド末尾に追加してから実行すること。

yum remove -y pacemaker pacemaker-libs pacemaker-cli pacemaker-cluster-libs corosync corosynclib crmsh crmsh-scripts pm_crmgen pm_logconv-cs pm_extras cluster-glue cluster-glue-libs resource-agents pssh; echo $?

リポジトリ同梱パッケージ(U0 の rpm -qa | grep -i repo で控えたもの)も削除する。名前は実環境の出力に置き換える:

yum remove -y pacemaker-repo; echo $?

残りを確認する:

rpm -qa | grep -Ei 'pacemaker|corosync|crmsh|pm_|cluster-glue|pssh|parallax'
確認
  • 出力が空になること。残っていたらその名前を指定して追加 remove する。
  • libqb 等の汎用ライブラリが Red Hat 署名版で残るのは深追い不要(この後の RHEL8 化で OS ごと入れ替わるため)。ただし U0 で「署名なし」だったものは消し切ること(rpm -qi パッケージ名 | grep Vendor で判別できる)。
STEP U4

残存物の掃除

複製機・全ノード

説明: rpm は「自分が配ったファイル」しか消さない。運用中に生成された設定・データ・ログ・ユーザー・repo 定義は手で消す。

U4-1. 設定・データ・ログ

cluster-glue 系が使う /var/lib/heartbeat が対象に含まれるのが、pcs 構成との違い。

rm -rf /etc/corosync /etc/pacemaker /var/lib/pacemaker /var/lib/corosync /var/lib/heartbeat
rm -rf /var/log/cluster; rm -f /var/log/ha-log* /var/log/pacemaker.log* /var/log/pm_logconv*

U4-2. サードパーティリポジトリの残骸

ls /etc/yum.repos.d/

U0 で控えた Linux-HA 系の repo ファイル(例: pacemaker.repo)が残っていれば rm -f で削除する。また、同梱 RPM の置き場が /opt 等にあれば削除する:

ls -d /opt/*linux-ha* /opt/*pacemaker* 2>/dev/null

U4-3. 管理ユーザー・ファイアウォール・hosts

userdel hacluster; groupdel haclient 2>/dev/null; echo "user cleanup done"
firewall-cmd --state && firewall-cmd --permanent --remove-port=5405/udp; firewall-cmd --reload
確認
  • haclient は userdel 時に一緒に消えることが多く、groupdel が「存在しない」と言うだけなら問題なし。
  • firewalld が「not running」/「NOT_ENABLED」の場合はスキップで OK(crmsh 構成では firewalld 不使用のケースも多い)。iptables 直書き運用なら /etc/sysconfig/iptables 内の 5405/udp 等の行を確認する。
  • /etc/hosts のクラスタ用エントリは、RHEL8 で同名・同 IP で組み直すなら残す判断も可(ここだけ任意)。
STEP U5

アンインストール完了の判定(6 項目)

複製機・全ノード

説明: 以下 6 項目がすべて「空」または「無し」になったら Pacemaker の撤去完了。①②がパッケージ層、③④が稼働層、⑤⑥が生成物層に対応する(付録 A-1)。各コマンドに >> /root/uninstall-after-check.txt 2>&1 を付けて証跡を残すこと。

# ① パッケージが残っていない(空が正)
rpm -qa | grep -Ei 'pacemaker|corosync|crmsh|pm_|cluster-glue|pssh|parallax'
# ② サービス定義が残っていない(空が正)
systemctl list-unit-files | grep -Ei 'pacemaker|corosync|logconv'
# ③ プロセスが動いていない(空が正)
ps -ef | grep -Ei 'pacemaker|corosync|logconv' | grep -v grep
# ④ クラスタ用ポートが閉じている(空が正。5404/5405=corosync、3121=pacemaker-remote)
ss -tulpn | grep -E ':5404|:5405|:3121'
# ⑤ 設定・データディレクトリが存在しない(4 つとも No such file or directory が正)
ls -d /etc/corosync /var/lib/pacemaker /var/lib/corosync /var/lib/heartbeat 2>&1
# ⑥ 管理ユーザーと repo 残骸が存在しない(no such user かつ grep 空が正)
id hacluster; ls /etc/yum.repos.d/ | grep -i -E 'pacemaker|linux-ha'
確認
  • 6 項目すべてが「空 / No such file or directory / no such user」であること。1 つでも該当しない場合は、対応する STEP(①→U3、②③→U2、④→U2・U3、⑤→U4-1、⑥→U4-2・U4-3)に戻る。
  • 証跡ファイル /root/uninstall-after-check.txt に 6 項目の出力が保存されていること。

第 2 部: td-agent の撤去

構造の説明: td-agent は「オムニバス形式」といって、Ruby 本体からプラグインまで全部を /opt/td-agent 配下に自己完結で抱え込むパッケージ。Pacemaker と違って依存パッケージの芋づるがなく、削除自体は簡単。掃除すべきは「rpm が消さない生成物」= 設定・ログ・バッファ・追加プラグイン・専用ユーザー・repo 定義。

STEP F0

実態確認と安全確認

複製機・全ノード
事故ポイント ②

リスク: 複製機の td-agent が起動したままだと、本番と同じ設定で本番の集約先(転送先サーバや外部サービス)へログを二重送信している可能性がある。集約側のデータ汚れや二重カウントの原因になる。

対策: 下の is-active が active だったら、F1 のバックアップを取り次第、速やかに F2 の停止へ進む。

rpm -qa | grep td-agent
systemctl is-active td-agent
ls /etc/yum.repos.d/ | grep -i -E 'td|treasure|fluent'
確認
  • td-agent-3.5.1-0.el7.x86_64 が表示されること。
  • is-active の結果(active か inactive か)を控える。active なら事故ポイント②に該当。
  • Treasure Data リポジトリ定義(例: td.repo)のファイル名を控える(F4 で削除)。
STEP F1

設定のバックアップ

複製機・全ノード

説明: RHEL8 側では後継の fluent-package を導入するため、旧設定は移行の原本になる。特に追加インストールされたプラグインの一覧は rpm の情報からは分からず、消す前にしか取れない。

mkdir -p /root/td-agent-backup
cp -a /etc/td-agent /root/td-agent-backup/; echo $?
/opt/td-agent/embedded/bin/fluent-gem list > /root/td-agent-backup/plugin-list.txt; echo $?
cp -a /etc/logrotate.d/td-agent /etc/sysconfig/td-agent /root/td-agent-backup/ 2>/dev/null; ls /root/td-agent-backup/
確認
  • td-agent ディレクトリ(中に td-agent.conf)と plugin-list.txt が取れていること。
  • plugin-list.txt 内の fluent-plugin- で始まる行が追加導入プラグイン。fluent-package 再構築時に同等品を入れる必要があるものとしてマークしておく。
  • バックアップを閉域外にも複製したこと。
STEP F2

サービスの停止と自動起動解除

複製機・全ノード 
systemctl stop td-agent; echo $?
systemctl disable td-agent; echo $?
ps -ef | grep -E 'td-agent|fluentd' | grep -v grep
確認
  • ps の出力が空であること。td-agent は親子 2 プロセスで動くため、stop 後に必ず両方消えたことを確認する。

バッファについて: 本番機の停止なら「未送信バッファのフラッシュ」を考えるところだが、今回は削除前提の複製機なので不要。バッファは F4 でディレクトリごと削除する。

STEP F3

パッケージの削除

複製機・全ノード 
yum remove -y td-agent; echo $?
rpm -qa | grep -i -E 'td-agent|fluentd'
確認
  • echo $? が 0、rpm -qa の出力が空であること。
  • オムニバス形式なので、消えるのは基本この 1 個だけ(依存の芋づるは無いのが正常)。
STEP F4

残存物の掃除

複製機・全ノード 
rm -rf /opt/td-agent

/opt/td-agent は rpm が大半を消すが、運用中に fluent-gem で追加したプラグインのファイルは rpm の管理外なので、ディレクトリごと確実に消す。

rm -rf /etc/td-agent /var/log/td-agent /var/run/td-agent

/var/log/td-agent 配下にはバッファファイル(buffer/ 配下)とログ本体が残っている。ここにログの中身(業務データ)が含まれるため、複製機の廃棄・返却要件によってはこの削除が必須。

rm -f /etc/logrotate.d/td-agent /etc/sysconfig/td-agent
userdel td-agent; groupdel td-agent 2>/dev/null; echo "user cleanup done"
rm -f /etc/yum.repos.d/td.repo
確認
  • repo ファイル名は F0 で控えた実名に置き換えて削除したこと。
  • firewalld で 24224 等を開けていた場合(firewall-cmd --list-ports で確認)は --remove-port で閉じたこと。開けていなければ何もしなくてよい。
STEP F5

アンインストール完了の判定(6 項目)

複製機・全ノード

説明: Pacemaker 側 U5 と同じ 3 層 6 項目。すべて空 / 無しで完了と判定する。証跡は >> /root/uninstall-after-check.txt 2>&1 で追記保存する。

# ① パッケージが残っていない(空が正)
rpm -qa | grep -i -E 'td-agent|fluentd'
# ② サービス定義が残っていない(空が正)
systemctl list-unit-files | grep td-agent
# ③ プロセスが動いていない(空が正)
ps -ef | grep -E 'td-agent|fluentd|/opt/td-agent' | grep -v grep
# ④ 使用ポートが閉じている(空が正。24224=forward 受信、24220=monitor_agent、9880/8888=HTTP 系)
ss -tulpn | grep -E ':24224|:24220|:9880|:8888'
# ⑤ ディレクトリが存在しない(3 つとも No such file or directory が正)
ls -d /opt/td-agent /etc/td-agent /var/log/td-agent 2>&1
# ⑥ 専用ユーザーが存在しない(no such user が正)
id td-agent
確認
  • 6 項目すべてが「空 / No such file or directory / no such user」であること。該当しない項目があれば対応する STEP(①→F3、②③→F2、④→F2、⑤→F4、⑥→F4)に戻る。
  • ④ について、F1 で取得した td-agent.conf に上記以外のポート定義(source の port 指定)があれば、そのポートも grep 対象に追加して確認すること。

STEP Z

RHEL8 化工程への引き継ぎ前の最終確認

複製機・全ノード

説明: RHEL7 → 8 のバージョンアップ(leapp)は、サードパーティ RPM や残存 repo 定義が事前チェック(preupgrade)の阻害要因になる。「先にきれいに消してから上げる」という本方式の趣旨に沿って、最後にサードパーティの痕跡ゼロを確定させる。

# サードパーティ repo 定義が残っていないこと(Red Hat / RHUI 標準の定義のみが正)
ls /etc/yum.repos.d/
# U5・F5 の証跡が揃っていること
cat /root/uninstall-after-check.txt
# 撤去後の全パッケージ一覧を保存(バージョンアップ前後の比較用スナップショット)
rpm -qa | sort > /root/pkgs-after-uninstall.txt; echo $?
確認
  • /etc/yum.repos.d/ に Linux-HA 系・Treasure Data 系の定義が1 つも無いこと。
  • 証跡ファイルに U5 の 6 項目と F5 の 6 項目(計 12 項目)の出力が入っていること。
  • バックアップ 3 点セット(/root/crm-config-backup.crm ほか HA 系一式 / /root/td-agent-backup/ 一式 / 証跡ファイル類)が閉域外に複製済みであること。RHEL8 化でこのマシンの中身は変わるため、マシン内のコピーだけでは保険にならない。

付録A: 判定の考え方と詰まったときの対処

A-1

「インストール前の状態に戻った」の判定は 3 層で行う

アンインストールの完了は「yum remove が成功した」ことではなく、次の 3 層すべてが空になったことで判定する。U5 / F5 の 6 項目はこの 3 層に対応している。

① パッケージ層rpm データベース上に対象パッケージとサービス定義が存在しない(判定項目 ①②)
② 稼働層プロセスが動いておらず、使用していたポートが閉じている(判定項目 ③④)
③ 生成物層rpm が消してくれない運用生成物 — 設定・データ・ログ・専用ユーザー・repo 定義 — が存在しない(判定項目 ⑤⑥)

「過不足なく」の解釈: インストール時に道連れで入った汎用ライブラリ(libqb、perl 部品等の Red Hat 署名版)は yum remove では消えないが、この後の RHEL8 化で OS のパッケージ群ごと入れ替わるため実害がなく、深追いしない。消し切る対象は「サードパーティ製品そのもの(署名なしパッケージ)と、その設定・データ・ユーザー・repo 定義」であり、それは本書の STEP で網羅している。

A-2

よくある詰まりと対処

  1. U1 で crm コマンドが失敗する → クラスタが既に停止している場合の正常な挙動。U1 末尾の補足のとおり cib.xml を直接コピーして先へ進む。
  2. userdel が「user is currently used by process」で失敗する → 該当ユーザーのプロセスが残っている。②③ の判定コマンドで残プロセスを特定し、stop してから userdel をやり直す。
  3. yum remove が依存関係エラーで失敗する → エラーに出たパッケージ名を確認し、それが U0 の一覧(=今回の削除対象)に含まれるなら remove コマンドに追加。含まれない(=残すべき OS 側パッケージが道連れになろうとしている)場合はコマンドをそのまま実行せず、エラー全文を保存して削除対象の切り分けを行う。
  4. 判定 ④ でポートが残っている → ③ でプロセスが残っているはず。stop 漏れ(付随サービス含む)を疑う。stop 直後は TIME_WAIT が数十秒残ることがあるため、少し待ってから再確認する。
  5. rm -rf の対象パスを打ち間違えそうで怖い → 本書のコマンドをコピペで実行していれば起きない(共通ルール 1)。パスを編集する必要が生じた場合は、先に ls -d そのパス で実在確認してから rm する。
