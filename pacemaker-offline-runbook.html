RUNBOOK / OFFLINE INSTALL — 02

RHEL8 オフライン環境への Pacemaker 2.1系(pcs / corosync)導入手順書

インターネット接続可能な作業用マシンで HA パッケージ一式を収集し、閉域のターゲットノード群へ持ち込んでクラスタを構築する。実際の作業で発生した障害 2 件(checksum エラー / モジュラリティエラー)の対策を手順に組み込み済み。

作業用マシン Azure 上の RHEL8(RHUI 構成 / subscription-manager 登録不要)。root で作業。
作業ディレクトリ: /mnt/offline-rpms-ha(/mnt は一時ディスク。注意事項参照)
ターゲットマシン 閉域環境の RHEL8。クラスタを組む全ノード(通常 2 台以上)。配置先: /opt/offline-rpms-ha
前提条件 作業用マシンと全ターゲットノードの RHEL8 マイナーバージョンが一致していること。
Pacemaker 2.1 系は RHEL 8.5 以降で提供される(バージョンは OS のマイナーバージョンに紐付き、任意には選べない。例: 8.10 → 2.1.7)。8.4 以前だと 2.0 系になるため注意。
導入対象 pcs / pacemaker / corosync / fence-agents-all / resource-agents(いずれも HighAvailability リポジトリから収集)
実施範囲の凡例 作業用マシン ネット接続可の収集マシンで実施 / ターゲット・全ノード 閉域の全ノードで実施 / 代表ノードのみ クラスタのうち 1 台でのみ実施

作業前の必読事項(全工程共通ルール)

  1. コマンドは手打ちせず、必ずコピー&ペーストで実行する(過去にタイプミスで障害発生)。
  2. 各コマンドの直後に echo $? を実行し、0 なら成功・0 以外なら失敗。0 以外なら画面出力を保存してから対処する。
  3. 各 STEP の確認が OK になるまで次へ進まない。
  4. 【重要】/mnt は Azure の一時ディスク。VM を停止(割り当て解除)すると中身が消える。作業は 1 セッションで STEP 6(tar 化)まで完了させ、tar.gz は必ず /root/ に出力する。日をまたぐ場合は tar.gz を先に退避する。
  5. 倉庫(ローカルリポジトリ)の中身を変更したら、必ず 4 点セットで回す: ① createrepo_c で目録再生成 → ② tar 再作成・再運搬 → ③ ターゲットで dnf clean all → ④ repolist で確認。
  6. 今回の実作業で障害が 2 件発生している。該当箇所(STEP 0 と STEP 7)の「実障害」枠を必ず読むこと。対策は手順自体に組み込み済みだが、飛ばすと再発する。

【作業用マシン】収集フェーズ

STEP 0

前回作業の痕跡掃除(GNOME/xrdp 収集の残骸を無効化)

作業用マシン
実障害 ①

症状: STEP 4 の dnf download 実行時に「incorrect checksum」エラーが出て、ダウンロード全体が失敗した。

原因: 前回の GNOME/xrdp オフライン作業で作った offline.repo(ローカル倉庫の定義)が残っており、dnf が依存計算のためにその古い目録を読み込もうとして、参照先の実体と目録の checksum が食い違った。古い dnf キャッシュも悪さをする。

対策: 本 STEP 0 として手順に組み込み済み。収集作業の前に必ず実施する。

まず、前回作業のリポジトリ定義が残っていないかを確認します。

ls /etc/yum.repos.d/
dnf repolist all 2>/dev/null
確認
  • offline.repo のような前回作成のファイルがあるか。
  • repolist に offline という名前のリポジトリが enabled で出ていないか。

残っていた場合のみ、削除ではなく退避します(前回環境を再現したくなった場合に戻せるようにするため)。

mv /etc/yum.repos.d/offline.repo /root/offline.repo.bak

ファイル名が違う場合は、実際のファイル名に読み替えて退避してください。redhat.repo や rh-cloud*.repo 等の元からあるファイルは触らないこと。

次に、dnf のキャッシュ(古い目録)を完全に捨てます。

dnf clean all
rm -rf /var/cache/dnf
dnf repolist
確認
  • 最後の dnf repolist がエラーなく完了し、目録の再取得が走ること。
  • 一覧に offline が出ていないこと。
  • BaseOS 系 / AppStream 系のリポジトリが出ていること(HighAvailability は次 STEP で有効化)。もし前回の作業の名残で BaseOS/AppStream が disabled になっていたら、dnf config-manager --set-enabled リポジトリID で戻す。
STEP 1

前提確認

作業用マシン 
cat /etc/redhat-release
whoami
df -h /mnt
確認
  • RHEL バージョンが 8.5 以上であること(2.1 系の必須条件)。かつ全ターゲットノードと一致していること(ターゲット側でも同じコマンドで確認しておく)。
  • whoami が root であること(一般ユーザーの場合は先に sudo -i)。
  • /mnt の空きが 5GB 以上あること(Pacemaker 一式は依存込みでも通常 1GB 未満)。
STEP 2

HA リポジトリの確認と有効化

作業用マシン

説明: Pacemaker 関連(pacemaker / corosync / pcs / fence-agents 類)は BaseOS や AppStream ではなく「HighAvailability」という専用リポジトリで配布されています。まず、このマシンからそのリポジトリが見えるかを確認します。

dnf repolist all 2>/dev/null | grep -i -E 'high|ha-'
確認
  • highavailability を含む行が出ること(repo ID の例: rhui-rhel-8-for-x86_64-highavailability-rhui-rpms)。行末が disabled でも、存在すれば OK。
  • 1 行も出ない場合は、この STEP の末尾「行が 1 つも出ない場合」へ。

表示された repo ID を使って有効化します。下の repo ID は例。必ず実際の出力の ID に置き換えること。

dnf config-manager --set-enabled rhui-rhel-8-for-x86_64-highavailability-rhui-rpms
dnf repolist | grep -i high
確認
  • 有効なリポジトリ一覧に highavailability が表示されること。

行が 1 つも出ない場合: Azure の通常 RHEL イメージには HA リポジトリが付いていないことがある(HA リポジトリ付きは「RHEL with HA」という別イメージ)。その場合は、① Azure 上に「RHEL 8 with HA」イメージで作業用 VM をもう 1 台立てる(前回と同じ RHUI 構成のままにできるので確実)、② Red Hat アカウントで subscription-manager register して HA repo を有効化する、のいずれかで対応する。詳細は付録 A-5。

STEP 3

対象パッケージの存在確認と 2.1 系バージョン確認

作業用マシン

説明: 導入する 5 点の役割は以下です。

pacemakerクラスタ制御の本体(リソースの起動・停止・フェイルオーバー判断)
corosyncノード間の生存監視と通信層。Pacemaker の土台
pcsクラスタを操作する管理コマンド + 管理デーモン(pcsd)。実作業はほぼこれ経由
fence-agents-all障害ノードを強制停止する「フェンシング」用エージェント集
resource-agentsIP アドレスやファイルシステム等をクラスタ管理するための部品集
LANG=C dnf info pcs pacemaker corosync fence-agents-all resource-agents > /root/ha-pkg-check.txt; echo $?
grep -c "Name" /root/ha-pkg-check.txt
確認
  • echo $? が 0。
  • grep の結果が 5 以上(5 つとも見つかっている)。
  • 「No matching packages」が出る場合は STEP 2 が未完。

ダウンロード前に、実際に取得される Pacemaker のバージョンを目で確認します。

LANG=C dnf info pacemaker | grep -E '^(Name|Version)'
確認
  • Version が 2.1.x であること。
  • 2.0.x の場合は作業用マシンが RHEL 8.4 以前。ターゲットとバージョンが揃っているかを含め、前提から見直す(2.1 系にするには両側とも 8.5 以降が必要)。
STEP 4

RPM を一括ダウンロード

作業用マシン

説明: --resolve --alldeps で、作業用マシンにインストール済みかどうかを無視して、依存関係ごと全部かき集めます(ターゲットに何が入っているか分からないため)。

mkdir -p /mnt/offline-rpms-ha
cd /mnt/offline-rpms-ha
dnf download --resolve --alldeps --downloaddir=/mnt/offline-rpms-ha pcs pacemaker corosync fence-agents-all resource-agents; echo $?
ls /mnt/offline-rpms-ha/*.rpm | wc -l
確認
  • echo $? が 0。
  • RPM 個数が目安 80〜250 個(fence-agents-all が依存を多く引き込むため幅がある)。1 桁ならダウンロード失敗。
実障害 ① 関連

ここで「incorrect checksum」が出た場合は STEP 0 の掃除が不足している。付録 A-1 の切り分けを実施してから再実行する。なお dnf download は再実行すれば上書きで取り直すため、途中まで溜まった RPM フォルダを消す必要はない。

STEP 5

倉庫化して依存検証

作業用マシン

説明: ただの RPM ファイルの山を、dnf が「倉庫」として認識できるように目録(repodata)を生成します。

createrepo_c /mnt/offline-rpms-ha; echo $?
ls /mnt/offline-rpms-ha/repodata/repomd.xml
確認
  • repomd.xml が存在すること(前回、これが無くて詰まった)。

次に、運搬する前に「この倉庫だけでインストールが完結するか」をリハーサルします。--assumeno なので実際にはインストールされません。

dnf install --assumeno --disablerepo="*" --repofrompath=offline-test,/mnt/offline-rpms-ha --setopt=offline-test.gpgcheck=0 pcs pacemaker corosync fence-agents-all resource-agents
確認
  • 依存関係の一覧が表示された後、「Operation aborted」(no と答えた扱い)で終われば OK。
  • 「nothing provides 〜」等のエラーが出たら NG。そのパッケージ名を STEP 4 のコマンド末尾に追加して再ダウンロードし、createrepo_c からやり直す(共通ルール 5 の 4 点セット)。

このリハーサルは作業用マシン視点の計算のため完全ではないが、--alldeps で取得していれば実用上ここを通れば大丈夫。なお、実障害②(モジュラリティ)はこのリハーサルでは検出できない(本物のリポジトリが生きている作業用マシン上では発生しないため)。対策は STEP 7 に組み込み済み。

STEP 6

tar で固める

作業用マシン 
tar czf /root/offline-rpms-ha.tar.gz -C /mnt offline-rpms-ha; echo $?
ls -lh /root/offline-rpms-ha.tar.gz
確認
  • ファイルが存在し、サイズが数百 MB 程度あること。
  • 出力先が /root/ であること(/mnt に置いたままにしない。VM 停止で消えるため)。

-C /mnt を付けているので、展開時に /opt/root/... のような余計な深い階層はできない(前回発生した事象の再発防止)。この tar.gz を USB 等でクラスタを組む全ノードの /root/ に運搬する。

【ターゲットマシン】導入フェーズ(全ノードで実施)

STEP 7

展開とリポジトリ登録(モジュラリティ対策込み)

ターゲット・全ノード
実障害 ②

症状: STEP 8 のインストールが途中まで進んだ後、「No available modular metadata for modular package」エラーで失敗した。

原因: RHEL8 特有の「モジュラリティ」機構。AppStream 由来のパッケージの一部(perl / python 系など、fence-agents の依存で混入)は「モジュール」に属しており、本物のリポジトリには通常の目録に加えてモジュール用の目録(modules.yaml)が入っている。ところが STEP 5 の createrepo_c は通常の目録しか作れないため、ターゲットの dnf が「モジュール所属のはずなのに目録が無い」と判断してインストールを拒否した。

対策: repo 定義に module_hotfixes=1(このリポジトリはモジュール管理の対象外として扱え、という指示)を入れる。下の repo ファイルに組み込み済みなので、この STEP をそのまま実施すれば再発しない。正攻法(モジュール目録の合成)は付録 A-2 の対処法 B。

tar.gz を /root/ に置いた前提です。展開します。

tar xzf /root/offline-rpms-ha.tar.gz -C /opt/; echo $?
ls /opt/offline-rpms-ha/repodata/repomd.xml
確認
  • repomd.xml が存在すること。無い場合は付録 A-3 参照。
  • /opt/root/... のような深い階層になっていないこと(なっていたら付録 A-3)。

リポジトリ定義を作成します。6 行目の module_hotfixes=1 が実障害②の対策です。絶対に省かないこと。

tee /etc/yum.repos.d/offline-ha.repo << 'EOF'
[offline-ha]
name=Offline HA Local Repository
baseurl=file:///opt/offline-rpms-ha
enabled=1
gpgcheck=0
module_hotfixes=1
EOF
dnf clean all
dnf --disablerepo="*" --enablerepo="offline-ha" repolist
確認
  • repolist に offline-ha が表示され、エラーが出ないこと。
  • cat /etc/yum.repos.d/offline-ha.repo で module_hotfixes=1 の行が入っていることを目視確認。

module_hotfixes=1 の注意点: モジュールのバージョン整合チェックを丸ごと無効にする設定。今回のように「1 つの作業用マシンから一度に収集した整合の取れたパッケージ群」を入れる分には実害はまずないが、この repo を恒久的に置いて後から別のパッケージを混ぜていく使い方には向かない。全 STEP 完了後に STEP 11 で無効化する。

STEP 8

インストール

ターゲット・全ノード 
dnf --disablerepo="*" --enablerepo="offline-ha" install -y pcs pacemaker corosync fence-agents-all resource-agents; echo $?
rpm -q pcs pacemaker corosync
確認
  • echo $? が 0。
  • rpm -q で 3 つともバージョン付きで表示されること(「is not installed」が出たら NG)。
  • pacemaker のバージョンが 2.1.x であること(最終確認)。

「No available modular metadata」が再発した場合は、STEP 7 の repo ファイルに module_hotfixes=1 が入っていない(付録 A-2)。依存パッケージ不足のエラーが出た場合は付録 A-4。なお dnf のトランザクションはチェック段階で止まるため、エラーで失敗しても中途半端にインストールされている心配はほぼない(rpm -q で全部「is not installed」ならクリーンな状態)。

STEP 9

ノード共通の初期設定

ターゲット・全ノード

9-1. ノード名の相互解決(閉域では特に重要)

説明: クラスタはノード同士が名前で通信する。閉域環境は DNS が無いことが多いので、/etc/hosts に全ノードを登録する。IP とホスト名は実環境の値に置き換えること。全ノードで同じ内容にすること。

tee -a /etc/hosts << 'EOF'
192.168.10.11  node1
192.168.10.12  node2
EOF
ping -c 2 node1; ping -c 2 node2
確認
  • 全ノード名に対して ping が返ること。
  • 3 ノード以上の構成の場合は、その分の行をすべて追加すること。

9-2. hacluster ユーザーのパスワード設定

説明: インストール時に hacluster という管理用ユーザーが自動作成されている。ノード間の認証に使うのでパスワードを設定する。全ノードで同じパスワードにすること。

passwd hacluster

9-3. pcsd の起動とファイアウォール

systemctl enable --now pcsd
systemctl is-active pcsd
firewall-cmd --permanent --add-service=high-availability
firewall-cmd --reload
確認
  • is-active が active であること。
  • firewall-cmd が両方 success であること。
  • ここまでの STEP 7〜9 を全ノードで完了していることを確認してから STEP 10 へ。

【代表ノード 1 台のみ】クラスタ構築フェーズ

STEP 10

クラスタ作成と起動確認

代表ノードのみ

説明: ここからはクラスタ全体への操作なので、どれか 1 台(例: node1)でだけ実行する。node1 / node2 / mycluster は実環境の値に置き換える(ノード名は 9-1 で /etc/hosts に登録した名前と一致させること)。

まずノード間の相互認証。パスワードを聞かれたら 9-2 で設定したものを入力する。

pcs host auth node1 node2 -u hacluster
確認
  • 各ノードに Authorized と表示されること。失敗したら付録 A-6。
pcs cluster setup mycluster node1 node2; echo $?
pcs cluster start --all
pcs cluster enable --all
pcs status
確認
  • pcs status で全ノードが Online になっていること(反映まで数十秒かかることがある)。
  • Current DC 行のカッコ内に version 2.1.x-... と表示されること(2.1 系で稼働している最終確認)。

STONITH(フェンシング)について

この時点では pcs status に「no stonith devices and stonith-enabled is not false」という警告が出る。フェンシングは障害ノードを強制停止する仕組みで、本番運用では必須だが、設定方法はハードウェア(iLO/iDRAC、Azure なら fence_azure_arm 等)に完全に依存するため本書の範囲外とする。検証目的で一時的に警告を消すだけなら以下を実行できる:

pcs property set stonith-enabled=false

ただし、この状態での本番運用はスプリットブレイン(両系同時稼働によるデータ破壊)のリスクがあるため非推奨。本番移行時には必ず環境に合ったフェンス設定を行うこと。

STEP 11

後片付け(オフラインリポジトリの無効化)

ターゲット・全ノード

説明: module_hotfixes=1 付きのリポジトリを有効なまま恒久的に残すのは避けたい(STEP 7 の注意点参照)。また、今回の実障害①は「前回の offline リポジトリの残骸」が原因だった。同じ轍を次回作業で踏まないためにも、導入が完了したら無効化しておく。

sed -i 's/^enabled=1/enabled=0/' /etc/yum.repos.d/offline-ha.repo
dnf clean all
grep enabled /etc/yum.repos.d/offline-ha.repo
確認
  • enabled=0 と表示されること。
  • 後日この倉庫から追加インストールしたい場合は、enabled=0 のまま dnf --enablerepo=offline-ha install ... のように一時的に有効化して使えばよい(定義ファイルと /opt の実体は残しておく)。

付録A: トラブルシュート集

今回の実作業で発生した障害(A-1、A-2)と、起こり得る典型パターンをまとめる。

A-1

「incorrect checksum」で dnf download が失敗する ★実障害①

作業用マシン

症状: STEP 4 の dnf download がエラーで止まる。

原因: dnf download --resolve は依存計算のために有効な全リポジトリの目録を読み込む。前回作業の offline リポジトリ定義が有効なまま残っていて、参照先(/opt/offline-rpms 等)の中身が消えていたり変わっていたりすると、目録と実体の checksum が食い違い、処理全体が止まる。古い dnf キャッシュ単独でも起こり得る。なお「リポジトリを disable しているだけ」ならエラーは「パッケージが見つからない」系になるはずで、checksum エラーは目録の食い違いを示す。

対処(切り分け順):

  1. STEP 0 を最初から実施する(repo 残骸の退避 → キャッシュ全消し)。
  2. それでも出る場合、エラーメッセージにどのリポジトリ / どのパッケージで checksum が合わなかったかが書かれているので、該当リポジトリの定義を確認する。
  3. 必要なリポジトリ(BaseOS / AppStream / HighAvailability)が disable されていないかも dnf repolist all で併せて確認し、disabled なら dnf config-manager --set-enabled リポジトリID で戻す。
A-2

「No available modular metadata for modular package」 ★実障害②

ターゲット・全ノード

症状: STEP 8 のインストールが途中まで進んだように見えた後、このエラーで失敗する。

原因: STEP 7 の実障害②の枠を参照(createrepo_c はモジュール目録を作れない)。

対処法 A(推奨・ターゲット側だけで完結): repo ファイルに module_hotfixes=1 を入れる。STEP 7 の repo ファイルに組み込み済みなので、通常はこのエラー自体が出ない。出た場合は cat /etc/yum.repos.d/offline-ha.repo でこの行の有無を確認し、無ければ STEP 7 の tee コマンドを再実行 → dnf clean all → STEP 8 を再実行する。

対処法 B(正攻法・恒久的な正式リポジトリにしたい場合): 作業用マシンの dnf キャッシュに残っている本物のモジュール目録を抜き出し、ローカル倉庫に合成する。

作業用マシン で実施:

ls /var/cache/dnf/*/repodata/*modules*
確認
  • *-modules.yaml.gz(または .xz)が 1 つ以上出ること。何も出ない場合は dnf makecache を実行してから再確認。
mkdir -p /root/modmeta
for f in /var/cache/dnf/*/repodata/*modules*; do case "$f" in *.gz) zcat "$f";; *.xz) xzcat "$f";; *) cat "$f";; esac; done > /root/modmeta/modules.yaml
modifyrepo_c --mdtype=modules /root/modmeta/modules.yaml /mnt/offline-rpms-ha/repodata/; echo $?
ls /mnt/offline-rpms-ha/repodata/ | grep modules
確認
  • repodata 内に modules を含むファイルができていること。

あとは「repodata フォルダだけ再運搬」で済む:

tar czf /root/repodata-only.tar.gz -C /mnt/offline-rpms-ha repodata

ターゲット・全ノード で実施(既存の repodata を丸ごと入れ替える):

rm -rf /opt/offline-rpms-ha/repodata
tar xzf /root/repodata-only.tar.gz -C /opt/offline-rpms-ha/
dnf clean all

そのうえで STEP 8 を再実行する(この場合 repo ファイルは module_hotfixes なしでも通る)。

A-3

ターゲットでの展開結果がおかしい

ターゲット・全ノード

症状と対処(前回作業で実際に発生したパターン):

  1. /opt/root/offline-rpms-ha/ のような深い階層ができている → tar 作成時に -C を使わなかった場合の症状。作り直しは不要で、正しい位置に動かす: 
    mv /opt/root/offline-rpms-ha /opt/offline-rpms-ha
rm -rf /opt/root
    (repo ファイルの baseurl=file:///opt/offline-rpms-ha と実際の場所の一致が最終ゴール)
  2. RPM の個数が数個しかない(ls /opt/offline-rpms-ha/*.rpm | wc -l で確認)→ 作業用マシンでのダウンロードが不完全なまま固めた可能性。作業用マシン側で個数を確認し、必要なら STEP 4 からやり直す。
  3. repomd.xml が無い → 固める前の createrepo_c 忘れ。作業用マシンで STEP 5 を実行し、A-2 対処法 B と同じ要領で「repodata だけ再運搬」する。
A-4

STEP 8 で依存パッケージ不足のエラー

ターゲット・全ノード

原因: 作業用マシンとターゲットのインストール済みパッケージ構成の差。

対処: エラーに出たパッケージ名を STEP 4 のコマンド末尾に追加して作業用マシンで取り直し、共通ルール 5 の 4 点セット(createrepo_c → tar 再作成・再運搬 → dnf clean all → repolist)を回してから STEP 8 を再実行する。

A-5

STEP 2 で HA リポジトリが 1 つも見えない

作業用マシン

原因: Azure の通常 RHEL イメージ(RHUI 構成)には HighAvailability リポジトリの定義が含まれていないことがある。HA リポジトリ付きは「RHEL with HA」という別の課金イメージ。

対処(いずれか):

  1. Azure 上に「RHEL 8 with HA」イメージで作業用 VM をもう 1 台立てる。RHUI 構成のままなので subscription-manager 不要で、本書の手順がそのまま使える(推奨)。マイナーバージョンをターゲットに揃えることを忘れないこと。
  2. Red Hat アカウントを持っている場合は subscription-manager register で登録し、subscription-manager repos --enable=rhel-8-for-x86_64-highavailability-rpms で有効化する(この場合 STEP 2 の repo ID はこの名前になる)。
A-6

STEP 10 の pcs host auth が失敗する

代表ノードのみ

原因はほぼ次の 3 つのどれか。上から順に全ノードで確認する:

  1. /etc/hosts の内容が全ノードで一致していない、または auth に指定した名前と hosts の名前が違う(9-1 を全ノードで再確認)。
  2. pcsd が起動していない(全ノードで systemctl is-active pcsd が active か)。
  3. ファイアウォールが未開放(全ノードで firewall-cmd --list-services に high-availability が含まれるか)。

hacluster のパスワードが全ノードで同一かも確認する(9-2)。

付録B: 用語の最小まとめ

HighAvailability リポジトリPacemaker 関連を配布する専用リポジトリ。BaseOS / AppStream とは別で、STEP 2 での有効化が必要
モジュラリティRHEL8 の仕組みで、一部パッケージを「モジュール」として版数管理するもの。専用の目録(modules.yaml)が必要で、createrepo_c では生成できない(実障害②の根本原因)
module_hotfixes=1そのリポジトリのパッケージをモジュール管理の対象外として扱わせる repo 設定。モジュール目録なしでもインストール可能になる
フェンシング (STONITH)応答しなくなったノードを強制停止し、スプリットブレインを防ぐ仕組み。本番クラスタでは必須
スプリットブレインノード間通信断で両系が「自分が正」と思い込み同時稼働する障害。共有データ破壊の原因になる
haclusterpcs インストール時に自動作成される管理用ユーザー。ノード間認証に使う
pcsdpcs の管理デーモン。ノード間のクラスタ操作の窓口(TCP 2224 等。firewalld の high-availability サービス定義に含まれる)
4 点セット倉庫の中身を変更した際の必須手順: createrepo_c → tar 再作成・再運搬 → dnf clean all → repolist 確認
