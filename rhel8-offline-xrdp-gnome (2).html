RUNBOOK / OFFLINE INSTALL

RHEL8 オフライン環境への xrdp + GNOME 導入手順書

インターネット接続可能な作業用マシンでパッケージを収集し、閉域のターゲットマシンへ持ち込んでインストールする

作業用マシン Azure 上の RHEL8(RHUI 構成 / subscription-manager 登録不要)。root で作業。
作業ディレクトリ: /mnt/offline-rpms(容量不足のため /root から移動済み)
ターゲットマシン 閉域環境の RHEL8(ネット接続なし)。配置先: /opt/offline-rpms
前提条件 両マシンの RHEL8 マイナーバージョンが一致していること(例: 両方 8.10)
導入対象 GNOME デスクトップ一式(Server with GUI 相当)+ xrdp / xorgxrdp / tigervnc-server

作業前の必読事項(全工程共通ルール)

  1. コマンドは手打ちせず、必ずコピー&ペーストで実行する(過去に dowload / df 等のタイプミスで障害発生)。
  2. 各コマンドの直後に echo $? を実行し、0 なら成功・0 以外なら失敗。0 以外なら画面出力を保存してから対処する(130 は Ctrl+C 中断 = 引用符崩れ等でコマンドが未完のまま貼られた疑い)。
  3. 各 STEP の確認が OK になるまで次へ進まない。
  4. 【重要】/mnt は Azure の一時ディスク。VM を停止(割り当て解除)すると中身が消え、不足パッケージの追加や modules.yaml 注入などの修正がすべて巻き戻る(実際に repoclosure の解決済みエラーが復活した)。repoclosure 合格から STEP 6(tar 化)までを必ず 1 セッションで完了させ、tar.gz は /root/ に出力する。やむを得ず中断する場合は、中間状態でも一度 tar を /root/ に作って退避しておく(再開時は /mnt へ展開して続きから)。
  5. 倉庫(リポジトリ)の中身を変更したら、必ず5点セットで回す:
    ① dnf download(追加取得)→ ② createrepo_c .(倉庫ディレクトリで目録更新)→ ③ modifyrepo_c --mdtype=modules modules.yaml repodata/(モジュール目録の再注入)→ ④ dnf clean all(古いキャッシュ破棄)→ ⑤ dnf repoclosure + echo $?(再判定)。
    createrepo_c は repodata を作り直すため、②を実行するたびに③のモジュール注入が必須(③を忘れるとターゲットで「No available modular metadata for modular package」が再発する)。②〜④を飛ばすと同じエラーが再現する。
  6. 全コマンドは root で実行する。プロンプト末尾が # なら root、$ なら一般ユーザー(その場合 sudo -i で root になる)。一般ユーザーで dnf を実行すると、RHUI のクライアント証明書が読めず Curl error (58) ... Permission denied が発生する。

全体の流れ

【作業用マシン(Azure / ネット接続可)】
  STEP 1  前提確認
  STEP 2  リポジトリ準備(BaseOS / AppStream は RHUI 名、EPEL)
  STEP 3  GNOME のパッケージ一覧を作成(/mnt/offline-rpms)
  STEP 4  RPM を一括ダウンロード
  STEP 5  倉庫化 → モジュール目録の注入 → 依存検証(repoclosure 不足ゼロまで)
  STEP 6  tar 化(出力は /root/)→ チェックサム取得
       │
       ▼ 手元 PC 経由で USB 等により閉域環境へ運搬
【ターゲットマシン(閉域 / ネット不可)】
  STEP 7  展開(/opt/)とローカルリポジトリ登録
  STEP 8  インストール(GNOME 一式 → xrdp)
  STEP 9  起動設定・ファイアウォール・接続確認

PHASE 1 — 作業用マシン(Azure・ネット接続可)

全コマンド root で実行(一般ユーザーの場合は先に sudo -i)
STEP 1

前提確認

cat /etc/redhat-release
whoami
確認
正常

Red Hat Enterprise Linux release 8.x (Ootpa) が表示され、バージョンがターゲット側と一致する。whoami が root。

異常

バージョン不一致 → 作業中止。作業用マシンをターゲットに合わせてから再開する。

STEP 2

リポジトリ準備

作業用ツールを導入する。

dnf install -y dnf-plugins-core createrepo_c
echo $?
which createrepo_c
確認
正常

Complete!(導入済みなら Nothing to do.)、$? が 0、/usr/bin/createrepo_c が表示される。

倉庫の一覧を確認する。

dnf repolist
確認 — 次の 3 種類が揃っていること
正常

・rhel-8-for-x86_64-baseos-rhui-rpms(baseos + rhui を含む名前)

・rhel-8-for-x86_64-appstream-rhui-rpms(appstream + rhui を含む名前)

・epel

※ RHUI(クラウド提供リポジトリ)構成のため subscription-manager での登録・有効化は不要。リポジトリ名の細部はイメージにより異なるが、baseos / appstream の文字が入った有効な倉庫が 1 つずつあればよい。

異常

epel が無い場合のみ以下を実行し、再度 dnf repolist で確認する。

dnf install -y https://dl.fedoraproject.org/pub/epel/epel-release-latest-8.noarch.rpm

このコマンド自体が通信エラーになる場合は、プロキシ/FW で dl.fedoraproject.org が遮断されている。ネットワーク管理者に確認する。

STEP 3

GNOME のパッケージ一覧を作成

作業フォルダを作成して移動する。STEP 3〜6 はすべてこの場所で実行する。

mkdir -p /mnt/offline-rpms
cd /mnt/offline-rpms
pwd
確認
正常

pwd の結果が /mnt/offline-rpms と 1 文字違わず一致する。

再掲: /mnt は一時ディスク。VM 停止で消えるため、本日中に STEP 6 まで完了させること。

3-1. 環境グループ → グループ一覧(「Server with GUI」はグループの束=環境グループのため 2 段階で展開する)

LANG=C dnf group info "Server with GUI" > env-info.txt
echo $?
awk '/Groups:/{sec=$0} /^   /{if (sec ~ /Mandatory/) {sub(/^ +/,""); print}}' env-info.txt > group-list.txt
echo $?
cat group-list.txt
確認
正常

Core / base-x / GNOME 等のグループ名が 1 行ずつ、5〜15 行程度並ぶ。

異常

$? が 130 → Ctrl+C 中断。貼り付け時に awk の引用符 ' が欠落・文字化けし、継続プロンプト > で入力待ちになった状態。行頭と行末に ' が計 2 つあることを目視してから貼り直す。改善しない場合はコマンドをファイル(.sh)に保存して bash ファイル名 で実行する。

0 行 → env-info.txt が英語出力か確認(grep Mandatory env-info.txt)。出なければ 1 本目の LANG=C の付け忘れ。

3-2. 各グループ → パッケージ一覧

while IFS= read -r g; do LANG=C dnf group info "$g"; done < group-list.txt > group-info.txt
echo $?
awk '/Packages:/{sec=$0} /^   /{if (sec !~ /Optional/) {sub(/^ +/,""); print}}' group-info.txt | sort -u > package-list.txt
echo $?
wc -l package-list.txt
head -20 package-list.txt
grep -E '[^a-zA-Z0-9._+-]' package-list.txt   # 壊れ検知(何も出ないのが正常)
確認
正常

行数が 300 前後(250〜450 許容)。head の表示が英数字のパッケージ名のみ。grep(壊れ検知)が何も表示しない。

異常

行数が数十以下 → 3-2 の 1 本目からやり直し。grep で行が出た → その行は混入物なので vi package-list.txt で削除する。

STEP 4

RPM を一括ダウンロード

現在地と空き容量を確認してから開始する(過去にディスク満杯で Curl error (23): Failed writing received data to disk が発生)。

pwd          # /mnt/offline-rpms であること
df -h /mnt   # 空きが 5GB 以上あること

4-1. GNOME 一式(数十分かかる)

dnf download --resolve --alldeps $(cat package-list.txt) --downloaddir=/mnt/offline-rpms
echo $?
ls /mnt/offline-rpms/*.rpm | wc -l
確認
正常

$? が 0。RPM 個数が数百〜1000 前後。

異常

No package ○○ available + exiting due to strict setting → ○○ を grep "○○" package-list.txt で確認し、一覧から削除して再実行(RHUI 環境では提供されない管理系パッケージが混ざることがある。削除した名前は控えておく。最終判定は STEP 5 の repoclosure が行う)。

Curl error (23) / Failed writing ... to disk → ディスク満杯。dnf clean packages で掃除し、df -h で空きを確認して同じコマンドを再実行(取得済み分はスキップされ続きから進む)。

通信系エラー(Cannot download 等)→ 同じコマンドをそのまま再実行。

4-2. xrdp 関連(EPEL から取得)

dnf download --resolve --alldeps xrdp xorgxrdp tigervnc-server --downloaddir=/mnt/offline-rpms
echo $?
ls /mnt/offline-rpms/ | grep -E '^(xrdp|xorgxrdp|tigervnc-server)-'
確認
正常

3 種類の RPM ファイル名がすべて表示される。

異常

No package xrdp available → EPEL が無効。STEP 2 の dnf repolist 確認へ戻る。

4-3. 既知の不足の先回り適用 — 過去の repoclosure 検証で判明した不足・残骸への対処。/mnt 消失後のやり直し時も、このステップを実施すれば同じエラーの再発を防げる。

# (1) 既知の不足パッケージ(条件付き依存 4 件 + grub2 は BIOS/UEFI 両対応)を一括取得
dnf download --resolve --alldeps flatpak-selinux tigervnc-selinux grub2-pc grub2-efi-x64 selinux-policy-targeted --downloaddir=/mnt/offline-rpms
echo $?

# (2) 古い残骸 alsa-ucm-1.1.6 の削除(要求先 alsa-lib=1.1.6 がリポジトリに存在せず解決不能)
rm -f /mnt/offline-rpms/alsa-ucm-1.1.6*.rpm
ls /mnt/offline-rpms/ | grep alsa   # 1.1.6 が消えていることを確認

# (3) 再発防止: 一覧からも alsa-ucm を除去(次回ダウンロード時から入らなくなる)
sed -i '/^alsa-ucm$/d' package-list.txt
grep alsa-ucm package-list.txt       # 何も表示されないのが正常
確認
正常

(1) の $? が 0。(2) の grep で alsa-ucm-1.1.6 が表示されない。(3) の grep が何も表示しない。

STEP 5

倉庫化・モジュール目録の注入・依存検証(最重要チェックポイント)

5-1. 倉庫化 — フォルダを dnf が扱える倉庫に変換(目録 repodata を生成)する。

cd /mnt/offline-rpms
createrepo_c .
echo $?
ls /mnt/offline-rpms/repodata/repomd.xml

5-2. モジュール目録(modules.yaml)の注入 — RHEL8 の AppStream は一部パッケージ(perl / python 系など)を「モジュール」機構で配布しており、createrepo_c が生成する通常目録にはモジュール情報が含まれない。この注入を省くと、ターゲットでのインストール時に Error: No available modular metadata for modular package が発生する(実際に発生済み)。

元の AppStream 倉庫からモジュール目録を取り出し、ローカル倉庫の目録に登録する:

# (1) 元倉庫のモジュール目録を dnf キャッシュに取得(root で実行すること)
dnf clean all
dnf makecache
echo $?
ls /var/cache/dnf/*appstream*/repodata/*modules*

# (2) ローカル倉庫へコピーして展開
cp /var/cache/dnf/*appstream*/repodata/*modules.yaml.gz /mnt/offline-rpms/modules.yaml.gz
cd /mnt/offline-rpms
gunzip -f modules.yaml.gz
ls -l modules.yaml

# (3) 目録にモジュール情報を注入
modifyrepo_c --mdtype=modules modules.yaml repodata/
echo $?
ls repodata/ | grep modules
確認
正常

(1) で modules ファイルのパスが表示され、(3) の後 ls repodata/ | grep modules で ○○○-modules.yaml.gz が表示される。

異常

(1) で Curl error (58) ... Permission denied → 一般ユーザーで実行している(RHUI 証明書が読めない)。sudo -i で root になってやり直す。

(1) で今回不要な倉庫(ansible 等)のエラーが出続ける → dnf config-manager --set-disabled ansible-2-for-rhel-8-x86_64-rhui-rpms で無効化してよい(必要なのは baseos / appstream / epel のみ)。

実行順序の罠: createrepo_c . を再実行すると repodata が作り直され、注入済みのモジュール情報が消える。順序は必ず「createrepo_c → modifyrepo_c」で、modifyrepo_c が常に最後。modules.yaml は /mnt/offline-rpms に置いたままにしておき(tar に含めて運搬しても害はない)、倉庫を更新するたびに再注入する。

5-3. 依存検証 — 「この倉庫だけで依存関係が完結しているか」を機械検証する。

dnf clean all
dnf repoclosure --repofrompath=test,/mnt/offline-rpms --repo=test --check=test
echo $?
確認
正常

何も報告されず $? が 0。これが合格判定。STEP 6 へ進む。

異常

package ○○ requires △△ が表示 → △△ が不足。以下の5点セットを不足ゼロになるまで繰り返す(通常 2〜3 周で収束)。

dnf download --resolve --alldeps △△ --downloaddir=/mnt/offline-rpms
createrepo_c .     # /mnt/offline-rpms で実行(忘れると同じエラーが再現)
modifyrepo_c --mdtype=modules modules.yaml repodata/   # モジュール目録の再注入(createrepo で消えるため毎回)
dnf clean all      # 古いキャッシュ破棄(忘れると同じエラーが再現)
dnf repoclosure --repofrompath=test,/mnt/offline-rpms --repo=test --check=test; echo $?

条件付き依存 (A if B) の表記 → 「B を入れるなら A も必要」の意味。安全のため A も倉庫に追加する。grub2 が要求された場合は BIOS/UEFI 両対応のため grub2-pc grub2-efi-x64 を追加する。既知の 4 件(flatpak-selinux / tigervnc-selinux / grub2 / alsa)が出た場合は STEP 4-3 の実施漏れなので、4-3 を実施してから 5点セットで再検証する。

以前解決したエラーが復活した場合 → /mnt(一時ディスク)消失によるやり直しで修正前に巻き戻った疑い。STEP 4-3 と STEP 5-2(modules.yaml も消えている)を再実施する。

古いバージョンの残骸(例: alsa-ucm-1.1.6 requires alsa-lib = 1.1.6 のように、古い版が同版のぴったり指定を要求)→ 要求している古い側の RPM を削除し、現行版を取得して揃える。

# 例: alsa の場合
ls /mnt/offline-rpms/ | grep alsa            # 新旧の混在を確認
dnf download --resolve --alldeps alsa-ucm --downloaddir=/mnt/offline-rpms  # 現行版が無ければ取得
rm -f /mnt/offline-rpms/alsa-ucm-1.1.6*.rpm  # 古い版のみ削除
# その後 createrepo_c → modifyrepo_c → clean all → repoclosure(5点セット)
STEP 6

tar 化と運搬準備(出力先は /root/)

tar.gz は消えない領域 /root/ に出力する(/mnt に置いたまま VM を停止すると消失する)。

tar czf /root/offline-rpms.tar.gz -C /mnt offline-rpms
echo $?          # tar は成功時に無言(0 が正常)
tar tzf /root/offline-rpms.tar.gz | head -5
ls -lh /root/offline-rpms.tar.gz
cp /mnt/offline-rpms/package-list.txt /root/   # 一覧もターゲットで使うため退避
sha256sum /root/offline-rpms.tar.gz             # ハッシュ値を控える
確認
正常

tar tzf の各行が offline-rpms/ で始まる。サイズが 1.5G〜3G 程度。sha256sum のハッシュ値をメモしておく。

異常

各行が mnt/offline-rpms/ 等の深い階層で始まる → -C /mnt が抜けている。tar を作り直す。サイズが数 MB → 中身が空。STEP 4 の個数確認に戻る。

運搬経路: ① Azure から手元 PC へダウンロード(scp / ストレージ経由)→ ② USB 等で閉域環境のターゲットへ。運搬するのは offline-rpms.tar.gz と package-list.txt の 2 ファイル。ターゲットの /root/ に配置する。

PHASE 2 — ターゲットマシン(閉域・ネット不可)

運搬ファイルは /root/ に配置済みの前提。root で実行
STEP 7

展開とローカルリポジトリ登録

運搬ファイルの破損チェック(多段コピーのため必須)。

ls -lh /root/offline-rpms.tar.gz /root/package-list.txt
sha256sum /root/offline-rpms.tar.gz
確認
正常

ハッシュ値が作業用マシンで控えた値と完全一致する。

異常

不一致 → 運搬中に破損。コピーからやり直す(展開しても Unexpected EOF 等で失敗する)。

展開する(/opt/offline-rpms が出来上がる)。

tar xzf /root/offline-rpms.tar.gz -C /opt/
echo $?
ls /opt/offline-rpms/repodata/repomd.xml
ls /opt/offline-rpms/*.rpm | wc -l   # 作業用マシンでの個数と一致すること
ls /opt/offline-rpms/repodata/ | grep modules   # モジュール目録が来ていること(無いと STEP 8 で modular エラー)

リポジトリ定義を作成する(5 行まとめてコピペで 1 ファイルができる)。

tee /etc/yum.repos.d/offline.repo << 'EOF'
[offline]
name=Offline Local Repository
baseurl=file:///opt/offline-rpms
enabled=1
gpgcheck=0
EOF
cat /etc/yum.repos.d/offline.repo
確認
正常

5 行が過不足なく表示され、baseurl の file: の後のスラッシュが 3 本(:// + 絶対パス先頭の /)であること。

キャッシュ初期化 → 倉庫認識 → インストールのドライラン(疑似実行)。

dnf clean all
dnf --disablerepo="*" --enablerepo="offline" repolist
dnf --disablerepo="*" --enablerepo="offline" install xrdp --assumeno
確認
正常

repolist に offline が表示される(「This system is not registered」警告は無視してよい)。ドライランで依存一覧が表示され「操作が中止されました(Operation aborted)」で終わる → 本番インストールも通る見込み。

異常

repolist が空 → repo ファイルの baseurl と ls /opt/ の実体パスを突き合わせる。Failed to download metadata → repodata 欠損。展開確認へ戻る。

STEP 8

インストール

GNOME 一式(グループ定義は倉庫に含まれないため、運搬した一覧を直接指定する)。途中の Is this ok [y/N]: は y。

dnf --disablerepo="*" --enablerepo="offline" install $(cat /root/package-list.txt)
echo $?

xrdp 関連。

dnf --disablerepo="*" --enablerepo="offline" install xrdp xorgxrdp tigervnc-server
echo $?
rpm -q xrdp xorgxrdp tigervnc-server gnome-shell
確認
正常

両方とも Complete! で終了し、rpm -q で 4 つすべてバージョン付きで表示される。

異常

No package ○○ available → 倉庫に不足。作業用マシンで 5点セット(取得→createrepo→modifyrepo→clean→repoclosure)を実施し、tar から再運搬する。is not installed がある → 該当 install をやり直す。

Error: No available modular metadata for modular package → 倉庫にモジュール目録が無い。STEP 5-2 の実施漏れ、または createrepo_c 再実行後の再注入漏れ。作業用マシンで STEP 5-2 を実施し、tar から再運搬する(再展開前に rm -rf /opt/offline-rpms で旧倉庫を削除)。応急処置として repo ファイルに module_hotfixes=1 を追記するとエラーは回避できるが、モジュール管理の不整合の火種になるため、恒久対応は modules.yaml 注入とする。

STEP 9

起動設定と接続確認

systemctl set-default graphical.target   # 起動時に GUI で立ち上げる
systemctl get-default                     # graphical.target と出れば OK
systemctl enable --now xrdp               # xrdp を起動+自動起動化
systemctl status xrdp                     # Active: active (running) を確認
firewall-cmd --permanent --add-port=3389/tcp   # RDP ポート開放(success と出る)
firewall-cmd --reload
firewall-cmd --list-ports                 # 3389/tcp が含まれること
reboot

再起動後の最終確認。

systemctl status xrdp | grep Active   # active (running)
ss -tlnp | grep 3389                  # LISTEN 行が表示されること
確認 — 接続テスト
正常

Windows の「リモートデスクトップ接続」でターゲットの IP アドレスへ接続 → RHEL のユーザー名/パスワードでログイン → GNOME デスクトップが表示されれば全工程完了。

※ コンソールでログイン中のユーザーとは別のユーザーで接続すること(同一ユーザーの同時ログインは不具合の原因)。

異常

接続不可の切り分け順: ① systemctl status xrdp(起動)→ ② ss -tlnp | grep 3389(待受)→ ③ firewall-cmd --list-ports(開放)→ ④ journalctl -u xrdp --no-pager | tail -20(ログ)。

付録 — 既知のトラブルと対処(本作業で実際に発生したもの)

1. No such command: dowload / タイプミス系

dnf → onf/df、download → dowload、--resolve のハイフン欠落など。手打ち禁止・コピペ徹底で防止。実行前に「コマンド名」「ハイフン 2 本ずつ」「$(cat ...) の形」を目視確認する。

2. echo $? が 130

Ctrl+C による中断。引用符や括弧が閉じないまま貼り付けられ、継続プロンプト > で入力待ちになった状態を中断した痕跡。コマンドの引用符を確認して貼り直す。> が出たら「閉じ忘れのサイン」と判断し、Ctrl+C で安全に抜けてよい。

3. Curl error (23): Failed writing received data to disk

ダウンロードは成功しているがディスク満杯で書き込めない状態。df -h で確認し、dnf clean packages で掃除、不足なら空きのある領域(本手順では /mnt)へ作業場所を移す。取得済み分は残っているため、同じコマンドの再実行で続きから進む。

4. repoclosure のエラーが繰り返し同じ内容で出る

追加取得後の createrepo_c .(目録更新)または dnf clean all(キャッシュ破棄)の実施漏れ。repoclosure は RPM ファイルではなく目録を見て判定するため、倉庫の中身を変えたら必ず4点セットで回す。

5. 古いバージョンの残骸による unresolved deps(alsa-ucm 1.1.6 の例)

失敗と再実行を繰り返す過程で古い版の RPM が紛れ込み、「同版のぴったり指定(= 1.1.6)」を要求し続けるケース。要求している古い側を削除し、現行版を取得して揃える。dnf のダウンロードは同名ファイルをスキップするため、一度紛れた古い版は手で削除しない限り残り続ける。

6. No package xrdp available

xrdp は EPEL にしか存在しない。dnf repolist に epel が無ければ epel-release を導入する。なお dnf install と dnf download は同じ倉庫を参照するため、片方が失敗する状態ではもう片方も失敗する(原因は 1 つ)。

7. Error: No available modular metadata for modular package(ターゲットでのインストール時)

RHEL8 の AppStream は一部パッケージをモジュール機構で配布しており、モジュール所属の RPM を入れるにはモジュール目録(modules.yaml)が必要。createrepo_c はこれを生成しないため、元倉庫からコピーして modifyrepo_c --mdtype=modules で注入する(STEP 5-2)。createrepo_c を再実行するたびに注入し直すこと(repodata が作り直され消えるため)。恒久対応は注入、応急処置は repo ファイルへの module_hotfixes=1 追記(不整合の火種になるため恒久策にはしない)。

8. Curl error (58): could not load PEM client certificate / Permission denied(作業用マシン)

RHUI リポジトリの認証に使うクライアント証明書は root しか読めないため、一般ユーザーで dnf を実行すると発生する。プロンプト末尾が $ なら一般ユーザー。sudo -i で root(末尾 #)になってやり直す。また、作業に不要な倉庫(ansible 等)がエラーを出し続ける場合は dnf config-manager --set-disabled 倉庫名 で無効化してよい。

9. 解決済みの repoclosure エラーが復活する(/mnt 消失による巻き戻り)

VM 停止(割り当て解除)で /mnt(一時ディスク)が消え、STEP 3〜4 をやり直すと、過去に適用した修正(不足パッケージの追加・alsa-ucm 残骸の削除・modules.yaml 注入)がすべて失われ、同じエラーが再発する。判別方法: ls -l /mnt/offline-rpms/env-info.txt の日時が直近ならやり直し=巻き戻りとみなす。対処: STEP 4-3(既知の不足の先回り適用)と STEP 5-2(modules.yaml 再注入)を再実施し、repoclosure 合格から tar 化(/root/ 出力)までを同一セッションで完了させる。
